# TriView 1.0.0a4 — R7 Physical Acceptance Runbook

## Purpose

This runbook executes the physical Linux Mint/X11 gates for TriView `1.0.0a4` without changing the public `main` branch or publishing a release.

The product candidate is immutable:

```text
PRODUCT_SHA=a8fd3209d6315cc7cc1870220b6c79e7296b45b3
VERSION=1.0.0a4
```

Do not substitute the current `release/1.0.0a4` branch head for `PRODUCT_SHA`. The branch may advance through evidence-only documentation commits while the product code under physical qualification remains fixed at the SHA above.

## Stop conditions

Stop the qualification immediately if any of these occurs:

- the checked-out product SHA is not exactly `a8fd3209d6315cc7cc1870220b6c79e7296b45b3`;
- the session is not X11;
- `xdotool`, `xwininfo`, `Xephyr` or `xauth` is missing;
- the stable TriView installation or workspace catalog changes during the isolated-candidate phase;
- any critical physical smoke item fails;
- the candidate writes to the MCF project's `.mcf` tree during read-only/orientation-only checks;
- a secret/token appears in TriView persistence;
- update/rollback cannot preserve the workspace catalog;
- any command below produces an unexpected result.

## Phase A — isolate the exact product candidate

Use an isolated Git worktree so the normal development checkout is not disturbed:

```bash
set -Eeuo pipefail
export PRODUCT_SHA=a8fd3209d6315cc7cc1870220b6c79e7296b45b3

git fetch origin
git cat-file -e "$PRODUCT_SHA^{commit}"
git worktree add --detach ../triview-r7-1.0.0a4 "$PRODUCT_SHA"
cd ../triview-r7-1.0.0a4

test "$(git rev-parse HEAD)" = "$PRODUCT_SHA"
test -z "$(git status --porcelain)"
```

The current candidate ID used by the existing installer remains `RC4-1.0.0A1`; it is an installer namespace, not the package version. Verify the actual resolved product SHA instead of inferring identity from that label:

```bash
export CANDIDATE_ROOT="$HOME/.local/share/triview-workspace-candidates/rc4-1.0.0a1"
export CANDIDATE_META="$CANDIDATE_ROOT/current/candidate-release.json"

python3 - "$CANDIDATE_META" "$PRODUCT_SHA" <<'PY'
```

## Phase I — prove MCF read-only behavior by digest

Use a real MCF v1.1 project for which the Mission Cockpit has canonical `.mcf` artifacts. Do not paste tokens into this document or shell history.

Set only the local project path:

```bash
export MCF_PROJECT_ROOT=/absolute/path/to/the/mcf-project
```

Before opening/refreshing the Cockpit:

```bash
(
  cd "$MCF_PROJECT_ROOT"
  find .mcf -type f -print0 \
    | sort -z \
    | xargs -0 sha256sum \
    | sha256sum
) | tee /tmp/triview-r7-mcf-before.sha256
```

Open the candidate Mission Cockpit, exercise repository detection, binding and continuity orientation, then repeat:

```bash
(
  cd "$MCF_PROJECT_ROOT"
  find .mcf -type f -print0 \
    | sort -z \
    | xargs -0 sha256sum \
    | sha256sum
) | tee /tmp/triview-r7-mcf-after.sha256

diff -u /tmp/triview-r7-mcf-before.sha256 /tmp/triview-r7-mcf-after.sha256
```

Required: `diff` exit `0`.

Inspect the TriView-local binding sidecar for forbidden credential fields without exposing values:

```bash
BINDINGS="${XDG_DATA_HOME:-$HOME/.local/share}/triview-workspace/mcf-bindings.json"
if [[ -f "$BINDINGS" ]]; then
  python3 - "$BINDINGS" <<'PY'
import json
import pathlib
import sys

forbidden = {"token", "authorization", "cookie", "bearer", "session_token"}
data = json.loads(pathlib.Path(sys.argv[1]).read_text(encoding="utf-8"))

def walk(value, path="$"):
    if isinstance(value, dict):
        for key, child in value.items():
            if str(key).lower() in forbidden:
                raise SystemExit(f"forbidden persisted credential key at {path}.{key}")
            walk(child, f"{path}.{key}")
    elif isinstance(value, list):
        for index, child in enumerate(value):
            walk(child, f"{path}[{index}]")

walk(data)
print("binding_credential_keys=none")
PY
fi
```

## Phase M — pre-publication update limitation

Do **not** attempt to force `1.0.0a4` through the stable updater during this qualification.

At the current product candidate:

- `--stable` resolves the latest already-published GitHub Release, which is still `v1.0.0a3` before promotion;
- `--testing` requires an enabled testing manifest and the current manifest version validator does not accept the PEP 440 alpha form `1.0.0a4`;
- `config/update-channels/testing.json` is intentionally disabled.

Therefore the real stable-update-to-`1.0.0a4` portion of R7 Task 6 is `BLOCKED` until a separately reviewed remediation or an explicitly approved alternative qualification path exists. Do not edit lifecycle scripts during physical acceptance.

Do not mark the overall update/rollback gate PASS while the pre-publication update limitation in Phase M remains unresolved.
